# UI 제작 지침: AI 슬롭 피하기

웹사이트·UI·HTML을 만들 때마다 이 문서를 먼저 읽고 따른다.
목표는 "AI가 만든 티"가 나지 않고, 이 제품과 이 사용자를 위해 **누군가 선택한 것처럼 보이는** 화면이다.

> 출처: "10 tells of a slop ui"(Pranav Desai, GeekNews #34370), Hallmark 안티 슬롭 디자인 스킬(Nutlope/hallmark, GeekNews #32321), GUI 상호작용 알파벳과 86개 사용성 지침(GeekNews #32160), "바이브 코딩으로 만든 대시보드가 형편없어 보이는 10가지 이유"(Kucharski, GeekNews #33651), SANE 최소 디자인 기준(JTech-CO/SANE, GeekNews #33776)

---

## 0. 핵심 원칙

1. **모든 요소는 이유가 있어야 한다.** 색, 배지, 아이콘, 애니메이션, 카드 하나하나에 "이게 없으면 사용자가 뭘 잃지?"라고 물었을 때 답이 없으면 뺀다.
2. **평균으로 수렴하지 않는다.** 아무 방향이 없으면 AI는 학습 데이터의 평균(보라 그라데이션, 3열 카드, Inter)을 낸다. 먼저 방향을 정하고 만든다.
3. **새로운 기본값도 슬롭이다.** 슬롭을 피하려다 크림/베이지 배경 + 세리프 디스플레이 폰트 + 세이지 그린 포인트 같은 "고급스러워 보이는 기본값"으로 옮겨가지 않는다. 금지 목록을 피하는 것보다 **이 브리프에 맞는 선택**을 하는 게 목적이다.
4. **화면은 기능 도구다.** 대시보드, 설정, 목록 화면을 랜딩 페이지처럼 꾸미지 않는다.
5. **컨트롤은 창의성을 발휘할 곳이 아니다.** 버튼, 폼, 메뉴, 링크, 대화상자, 알림, 아이콘, 체크박스·라디오, 탭, 검색은 사용자가 수십 년간 학습한 표준대로 쓴다. 새로움은 콘텐츠와 시각 표현에 쓴다.
6. **사용자가 기억하게, 추측하게, 기다리게 만들지 않는다.**
7. **절제: 나쁜 무언가보다 아무것도 없는 편이 낫다.** 더 꾸미기보다 먼저 불필요한 것을 뺀다. 장식보다 신호(Signal Above Needless Embellishment).
8. **금지 목록은 도구지 교리가 아니다.** 다크 모드, 카드, 흔한 폰트, 여백, 촘촘한 전문가용 화면, 레트로·네온 브랜드 자체가 잘못은 아니다. 문제는 **이유 없이 기본값으로** 나온 경우다. 모든 제품을 똑같은 베이지 미니멀 페이지로 만드는 것도 슬롭이다.

### 기존 화면을 고칠 때
- 브랜드 개성과 정상 동작하는 기능(다크 테마, 데이터, 필터 등)은 요청이 없으면 유지한다.
- 카피·정보 구조·브랜드는 두고 구조·위계·가독성만 개선하는 게 기본이다.
- 새 의존성, 분석 스크립트, 불필요한 런타임 코드를 추가하지 않는다.
- 바뀐 파일만 돌려주고, 검증하지 못한 부분은 명시한다.

## 1. 만들기 전에 정할 것

코드를 쓰기 전에 아래를 먼저 한두 줄로 정하고, 결과물과 함께 밝힌다.

- **이 화면의 사용자와 주 용도** (한 문장)
- **장르**: 에디토리얼 / 모던 미니멀 / 분위기형(다크 툴) / 플레이풀 / 기타
- **전체 구조(매크로구조)**: 벤토 그리드, 긴 문서형, 대형 헤드라인형, 수치 중심형, 작업대(워크벤치)형, 대화형 FAQ, 선언문형, 사진 중심형, 인용 중심형 등에서 브리프에 맞게 고른다.
- **같은 프로젝트에서 직전 결과물과 같은 구조를 반복하지 않는다.** 두 페이지가 색만 바꾼 같은 템플릿처럼 보이면 실패다.
- **디자인 토큰 먼저**: 색·폰트·간격·반경을 `:root` 변수로 정의하고, 이후 모든 값은 토큰으로만 참조한다.
  - 글자 크기는 5~6단계 스케일 안에서만 (예: 12 / 14 / 16 / 20 / 28 / 40)
  - 모서리 반경은 2~3단계만 (예: 없음 / 작게 / 크게)
  - 간격은 4px 또는 8px 배수 스케일만. 요소마다 제각각인 패딩 금지.
  - 스케일이 흐트러지면 화면이 동시에 빽빽하면서도 비어 보이고, 둥글면서도 각져 보인다.

## 2. 색

**하지 말 것**
- 장식용 그라데이션: 버튼, 배경, 카드 등 넣을 수 있는 곳마다 넣기
- 보라→파랑 / 보라→분홍 그라데이션 히어로 (가장 유명한 AI 표식)
- `background-clip: text`로 만든 그라데이션 헤드라인
- 보라·분홍·청록 오로라 블롭 배경, 흐릿한 원/3D 구체 떠다니는 장식
- 의미 없는 색 남발("무지개 토사물"): 필드마다, 카드마다 다른 색
- 순수 `#000000` 배경, 순수 `#ffffff` 표면
- 다크 배경 카드에 색깔 있는 글로우 그림자
- 중간에 즉흥적으로 넣은 인라인 색상값(`#5b6cff` 같은 것)

**할 것**
- 앵커 색 1개 + 포인트 색 1개. 나머지는 중립색.
- 대략 70(중립) · 20~30(보조) · 10(포인트) 비율. 가장 강한 강조색은 화면 면적의 5% 안팎으로 아낀다.
- 가능하면 OKLCH로 팔레트를 정의해 명도·채도를 일관되게 맞춘다.
- 색에는 의미를 준다: 상태, 강조, 위험 등. 의미 없는 색은 쓰지 않는다.
- 따뜻함이 필요하면 그라데이션 대신 **중립색을 앵커 색 쪽으로 살짝 틴트**
- 다크 모드에서 높이는 그림자 대신 **표면 밝기**로 표현
- 새 색이 필요하면 토큰에 먼저 추가하고 참조

## 3. 타이포그래피

**하지 말 것**
- Inter(또는 Roboto, Open Sans) 하나로 제목과 본문 전부 처리
- 개발 관련이면 무조건 JetBrains Mono, 기술 얘기에 `//` 장식 붙이기
- 제목 한 단어만 이탤릭으로 바꾸는 "에디토리얼 흉내"
- 모든 섹션 위에 `01 / FEATURES` 같은 대문자 모노 아이브로우
- 라벨은 왼쪽 좁은 칸, 제목은 오른쪽에 두는 2열 섹션 헤드

**할 것**
- 개성 있는 디스플레이 폰트 + 정돈된 본문 폰트 페어링. 선택 이유를 한 줄로 설명할 수 있어야 한다.
- **한국어 지원 확인**: 고른 폰트에 한글 글리프가 없으면 한글만 시스템 폰트로 떨어져 제각각이 된다. 한글을 지원하는 폰트를 고르거나 한글 대체 폰트를 명시한다.
- 필수 정보를 작은 글자로 만들지 않는다. 본문은 읽기 편한 크기(보통 15~16px 이상)로.
- 제목은 정체(roman). 강조는 굵기·포인트 색·밑줄로.
- 아이브로우는 기본적으로 쓰지 않는다. 진짜 순서가 있는 단계·챕터일 때만, 페이지당 1~2개, 제목 바로 위에 세로로.
- 숫자 열에는 `font-variant-numeric: tabular-nums`
- 곧은 따옴표 대신 둥근 따옴표, `--` 대신 `—`, `...` 대신 `…`

## 4. 레이아웃·구조

**하지 말 것**
- 똑같은 3열 기능 카드 그리드 (아이콘 위, 두 줄 제목, 세 줄 본문)
- 카드 안에 카드, 그 안에 또 작은 카드
- 한쪽(주로 왼쪽)에 두꺼운 색 띠가 있는 카드("손톱 카드")
- `min-height: 100vh` 꽉 찬 중앙 정렬 히어로 + 한 문장 + 큰 버튼 하나
- 모든 섹션 중앙 정렬, 모든 섹션 같은 패딩
- 공식 같은 AI 내비: 왼쪽 로고, 가운데 링크 4~5개, 오른쪽 CTA, 흰 배경, 하단 1px 선
- 공식 같은 AI 푸터: 링크 4열(Product/Company/Resources/Legal) + 소셜 아이콘 줄 + 저작권
- 박스 밖 SVG·아이콘·리스트 정렬이 어긋난 채로 두기
- `width: 100vw`, `z-index: 9999`

**할 것**
- 그리드를 깬다: 열 너비와 카드 높이를 다르게, 카드 하나를 빼고 여백으로, 또는 카드 없이 타이포 리듬으로
- 담는 층(컨테이너)은 하나만
- 테두리가 필요하면 사방 얇은 선, 또는 없이
- 히어로는 내용 높이만큼. 좌우로 치우치게 배치하고 한 문장 이상 담는다.
- 대칭은 한 번만 깨도 충분하다.
- 섹션 간격을 다르게: 하나는 조이고 하나는 넓힌다.
- 내비·푸터는 사이트 장르에 맞게 고른다(떠 있는 알약형, 신문 제호형, 한 줄 인라인, 편지 맺음형 등). 빵집에는 "Resources" 열이 없다.
- 정렬은 반드시 눈으로 확인한다.

## 5. 컴포넌트·아이콘·이미지

**하지 말 것**
- 구별할 상태가 없는 배지: 항상 활성인데 붙인 "active", 검증 로직 없는 "verified"
- 깜빡이는(pulsing) 배지·점
- 이모지를 아이콘으로 사용 (✨ 🚀 ⚡ 🔥 🎯 ✅)
- 아이콘 라이브러리 섞어 쓰기 (Material + Heroicons + Lucide + 이모지)
- 목적 없는 글래스모피즘 (특히 그라데이션 위에 겹친 것)
- 모두 똑같아 보이는 "브루탈리즘"
- 가짜 브라우저 창·폰 프레임·코드 창 크롬을 CSS로 그리기
- AI 일러스트 느낌(매끈한 블롭 캐릭터, 낙서풍 사람)
- 만질 수 없는데 돌아가기만 하는 Three.js 3D, 로티 애니메이션 남용

**할 것**
- 배지는 실제로 여러 상태가 있고 사용자가 구별해야 할 때만
- 아이콘은 한 프로젝트에 라이브러리 하나 (SaaS는 Lucide, 굵기 변형 필요하면 Phosphor, Tailwind/shadcn이면 Heroicons). 대부분의 기능 목록은 아이콘 없이도 된다.
- 글래스모피즘은 콘텐츠 위에 뜬 오버레이처럼 깊이를 전달할 때만
- 스크린샷은 실제 이미지를 `<figure>`에, 테두리는 얇은 선 정도로
- 로딩 스피너, 체크 표시 등은 CSS/SVG로 직접

## 6. 문구(카피)

**하지 말 것**
- "Elevate", "Seamless", "Next-Generation", "Supercharge", "Unleash", "Empower", "Revolutionize"
- H1 밑 회색 부제에 "최첨단 직관적 인터페이스로 ~의 힘을 경험하세요" 류
- "Welcome back, [이름] ✨" 같은 환영 문구
- 채팅 맥락이 새어 나온 문구: "Neovim에서 작성", "모던 C++20으로 제작", 프롬프트 냄새 나는 슬로건
- 지어낸 수치: "10배 빠름", "50,000개 팀이 신뢰", "99.9% 가동률", "+47% 전환"
- "Jane Doe", "John Smith", "Acme", "Nexus", "Pulse" 같은 자리표시 이름

**할 것**
- 기능을 설명하는 평범하고 구체적인 말
- 수치는 사용자가 준 것만. 없으면 `—` + "수치 확인 필요" 자리표시, 또는 수치 섹션 자체를 뺀다.
- 자리표시 이름은 대상 사용자에 어울리는 그럴듯한 이름, 제품명은 도메인에 맞는 구체적 이름
- 버튼·링크 라벨은 짧게 ("무료로 시작하기" → "무료 시작")

## 7. 모션·인터랙션

**하지 말 것**
- `transition: all`
- 모든 카드에 `hover:scale-105`
- 튕기는(bounce/elastic, overshoot) 이징
- 스크롤할 때마다 모든 섹션 fade-up
- 호버 시 그라데이션이 흐르는 효과, 커서 따라다니는 점
- 멈출 수 없는 자동 회전 캐러셀
- 사용자가 눈으로 확인한 저장에 "완료!" 축하 토스트
- 되돌릴 수 있는 작업에 "정말 삭제할까요?" 확인창
- 서서히 나타나는 포커스 링, 레이아웃을 밀어내는 토스트, 50ms 번쩍이는 스피너

**할 것**
- 애니메이션할 속성을 명시하고 ease-out 계열 사용
- 요소당 신호 하나 (1px 이동, 색 변화, 밑줄 중 하나)
- 첫 로드에 계획된 등장 한 번, 나머지는 그냥 그 자리에
- 삭제는 즉시 반영 + 실행 취소 토스트. 되돌릴 수 없는 작업만 확인창.
- 포커스 링은 즉시 표시. 툴팁은 호버 800ms 이상, 포커스 0ms.
- 스피너는 150ms 지연 후 표시 또는 최소 300ms 유지, 레이아웃을 알면 스켈레톤

## 8. 표준 컨트롤 문법

각 컨트롤에는 정해진 역할이 있다. **버튼은 실행, 폼·체크박스·검색은 입력, 메뉴·링크·탭은 이동, 대화상자·알림은 시스템 응답, 아이콘은 상징.** 겉모습과 역할을 섞지 않는다.

### 버튼
- 누를 수 있게 보여야 한다: 형태, 배경 대비, 눌림 상태. 평면화하다 장식과 구분이 안 되게 만들지 않는다.
- 레이블은 2~4단어, 동사 + 결과: "확인" 대신 "청구서 저장", "주문하기", "파일 3개 삭제"
- 화면마다 시각적으로 두드러진 기본 행동은 **하나만**
- 자주 쓰는 버튼은 크고 가깝게(Fitts의 법칙). 터치 목표는 최소 약 1cm(44px 안팎).
- 누르면 0.1초 안에 반응
- 비활성 버튼은 숨기지 말고 흐리게 + 왜 안 되는지, 어떻게 켜지는지 안내
- 읽기 흐름이 끝나는 곳(필드·콘텐츠 뒤)에 배치
- 분할 버튼은 두 영역 사이에 구분선, 작은 쪽도 충분한 크기. 지배적인 기본 명령이 없으면 일반 메뉴 버튼.

### 입력 폼
- **가장 강력한 개선은 필드 삭제.** 선택 필드도 읽고 판단하는 비용이 든다.
- 모든 필드에 입력 중에도 보이는 **바깥 레이블**. 플레이스홀더는 레이블이 아니다.
- 전화번호 괄호·공백·하이픈 등 다양한 형식을 받고 정리는 코드가 한다.
- 오류는 해당 필드 옆에 평이한 말로, 이미 입력한 값은 보존
- 검증은 입력 도중이 아니라 필드를 벗어날 때
- 날짜는 날짜 선택기 등 작업에 맞는 전용 컨트롤
- 관련 필드를 묶어 **한 열**로
- 제출 버튼은 "제출" 대신 결과("주문하기", "가입 완료")
- 예상 부담을 정직하게 표시("질문 3개, 40초"). 부풀리거나 줄여 말하지 않는다.

### 메뉴·내비게이션
- 카테고리명은 사용자의 말로. "Solutions", "Resources" 같은 모호한 분류 금지.
- 짧고 모호한 메뉴보다 **길고 명확한 메뉴**가 낫다(보이는 항목은 7±2 제한 불필요).
- 데스크톱에서는 최상위 탐색을 그대로 노출. 햄버거 메뉴는 모바일에서만.
- hover 대신 클릭으로 열기. hover가 꼭 필요하면 짧은 지연 + 대각선 이동 허용 영역.
- 계단식 메뉴는 2단계까지
- 현재 위치를 명확히 표시
- 정렬은 중요도·빈도순. 가나다순은 이름을 알고 찾을 때만.
- 가장 자주 쓰는 2~3개 명령은 메뉴에서 꺼내 버튼으로

### 링크
- 본문 링크는 **색 + 밑줄** 함께
- 링크가 아닌 것에 링크 서식 금지. 링크를 버튼처럼, 버튼을 링크처럼 꾸미지 않는다.
- "여기를 클릭", "더 알아보기" 금지. 목적지를 알 수 있는 문구, 중요한 단어를 앞에.
- 기본은 같은 탭. 예외(새 탭, PDF 등)는 링크에 표시.
- 링크가 많은 화면은 방문한 링크를 구분

### 대화상자(모달)
- 진행을 실제로 막아야 하는 결정, 되돌릴 수 없는 결과, 필수 입력에만. 계속 작업할 수 있으면 비모달.
- 버튼은 "확인/취소" 대신 결과("파일 3개 삭제" / "파일 유지"). "구독 취소" 질문 밑에 "취소" 버튼 같은 모호함 금지.
- 안전한 선택이 기본값, Esc는 항상 취소
- 대화상자 하나에 질문 하나, 1~2문장
- 대화상자 위에 대화상자 쌓기 금지
- 방문 직후 뉴스레터 오버레이 금지

### 알림·오류 메시지
- 원시 오류 코드나 "오류가 발생했습니다" 대신: 무엇이, 어디서 문제인지 + 한 문장 복구 방법
- "잘못된", "불법", "치명적" 등 사용자 탓하는 표현 금지
- 단순 확인은 토스트, 고칠 때까지 남아야 하는 오류는 인라인, 재앙적 상황만 모달
- 사용자가 조치해야 할 오류를 몇 초 뒤 사라지게 하지 않는다.
- 빨간색만으로 오류 표시 금지. **아이콘 + 색 + 문구** 함께.
- 불필요한 알림·배지를 줄인다(중요한 알림까지 무시하게 만든다).

### 아이콘
- 공간이 있으면 **텍스트 레이블**을 붙인다. 없으면 툴팁.
- 널리 인식되는 건 돋보기, 집, 톱니바퀴, 휴지통 정도. 레이블 없는 아이콘 버튼은 이런 소수에만.
- 검색, 설정 등 표준 은유는 그대로. 유행 때문에 학습된 아이콘을 다시 그리지 않는다.
- 같은 계열이되 작은 크기에서도 실루엣이 구분되게
- 파비콘은 16×16에서도 보이는 강한 형태 하나 + 브랜드 색

### 체크박스·라디오·토글
- 독립 선택은 체크박스(사각형), 하나만 고르는 건 라디오(원). 바꿔 쓰지 않는다.
- 선택지는 세로로 쌓고, **레이블 전체를 클릭 가능**하게
- 라디오 그룹은 적절한 기본값, 선택 안 함이 유효하면 "없음" 옵션
- 예/아니요는 라디오 2개 대신 체크박스 하나
- 선택지 2~4개는 드롭다운 대신 라디오로 모두 보여주기
- 토글은 **즉시 적용**되는 설정에만. 저장 버튼으로 확정한다면 체크박스. 토글 + 저장 버튼 조합 금지.
- 선택지는 긍정문으로, 이중 부정 금지

### 탭
- (이 사이트, 2026-10-07) 칩 · 탭은 버튼과 색으로 구분한다: 고른 칩은 옅은 보라 바탕(--color-primary-soft) + 보라 글씨(--color-primary) + 보라 테두리(--color-primary-light), 안 고른 칩은 흰 바탕 + 회색 글씨. 버튼은 모두 알약형이고 기본 버튼만 진한 보라를 칠한다. 여러 줄 선택지(장면 반응 · 유형 고르기 카드)는 버튼이 아니라 선택 카드라 반경 12를 쓴다.
- 같은 유형·수준의 병렬 콘텐츠에만(상세 / 리뷰 / 사양)
- 항상 **한 줄**. 레이블은 1~2단어.
- 선택·hover·비선택 상태를 구분하고, 선택된 탭은 패널과 붙어 보이게
- 가장 많은 사용자가 먼저 필요한 탭을 기본으로
- 순차 단계(결제 등)에는 탭 대신 단계 표시가 있는 마법사
- 비교해야 할 데이터를 탭으로 쪼개지 않는다(표로 함께)
- 가능하면 탭마다 고유 URL

### 검색
- 콘텐츠가 많은 사이트는 모든 페이지 상단에 **열린 검색창**(아이콘 뒤에 숨기지 않기)
- 최소 약 27자 보이는 너비
- 돋보기로 제출 표시 + Enter 지원
- 오타·복수형·동의어 허용
- 결과 페이지에서도 검색어를 창에 유지
- 결과에 제목 + 왜 일치했는지 보여주는 요약, 결과가 많으면 필터

### 스크롤·창·커서
- 스크롤재킹(속도·방향 가로채기) 금지
- 스크롤 가능한 영역에는 스크롤바를 보이게
- 푸터가 중요하면 무한 스크롤 대신 "더 보기"
- 중요한 콘텐츠를 위에. 순서가 곧 중요도다.
- 예고 없이 새 창 열기 금지(뒤로 가기가 깨진다)
- 손 커서는 실제 클릭 가능한 요소에만, I-beam은 편집 가능한 텍스트에만. 표준 커서를 임의로 꾸미지 않는다.
- 1초 넘게 걸리면 작업 중 표시

## 9. 대시보드·데이터 시각화

"보기 좋은 대화형 대시보드"를 만들면 차트와 필터는 나오지만, **무엇을 찾고 어디부터 볼지**는 정리되지 않는다. 대시보드의 일은 데이터를 다 보여주는 게 아니라 사용자 대신 정리해주는 것이다.

**만들기 전에**
- 이 대시보드가 답할 **핵심 질문 1~3개**를 먼저 정한다. 질문이 없으면 데이터 나열이 된다.
- 사용자 여정을 설계한다: 첫 화면에서 핵심 답 → 세부 비교 → 원자료 탐색 순서
- 배치 순서에 이유가 있어야 한다. "왜 이 차트가 맨 위인가?"에 답할 수 있어야 한다.

**하지 말 것**
- 모든 차트·카드를 같은 테두리, 같은 배경, 같은 크기로 (위계 없음)
- 빈 공간이 대부분인 차트에 첫 화면의 큰 영역 내주기 (데이터 분포를 먼저 확인)
- 모든 열을 쏟아 넣은 거대한 표, 화면 밖으로 잘리는 표
- 축 레이블 없는 차트, 의미를 알 수 없는 눈금, 모호한 약어("gpm")
- 차트와 떨어진 범례 (특히 범주당 요소가 하나뿐일 때)
- 막대 길이는 A를, 막대 끝 숫자는 B를 나타내는 식으로 두 지표를 한 차트에 섞기
- 같은 숫자(전체 건수 등)를 상단, 막대, 요약 카드에 반복해서 공간 채우기
- 테마 없이 "기술적인 느낌"의 어두운 배경 + 형광 강조색
- IBM Plex Mono, Archivo 같은 흔한 기본 조합 그대로 쓰기

**할 것**
- 가장 중요한 지표·차트 하나를 크게, 나머지는 작게. 크기·대비로 시선 순서를 만든다.
- 핵심 수치는 숫자로만 묻지 말고 비교할 수 있게 시각화한다(막대, 점 등).
- 축 제목과 단위를 명시하고, 약어는 풀어 쓴다.
- 범례 대신 데이터 옆에 직접 레이블
- 차트 하나에 지표 하나. 두 지표를 봐야 하면 차트를 나누거나 명확히 구분.
- 표는 핵심 열만 기본 노출하고 나머지는 펼치기·상세 보기로
- 같은 정보는 한 번만. 사실 하나에는 주된 자리 하나, 다른 곳에는 필요한 맥락만.
- 데이터를 지어내지 않는다. 근거 없는 비교("업계 평균 대비")도 만들지 않는다.
- 결측값(데이터 없음)과 로딩 중 상태를 구분해서 보여준다.
- 필요한 수치는 hover 툴팁 없이도 보이게. 툴팁은 보조로만.
- 라벨에는 단위, 범주, 기간, 의미를 그 자리에서 알 수 있게 붙인다.
- 색은 데이터 의미 중심으로 일관되게(같은 범주는 모든 차트에서 같은 색). 팔레트에 하나의 시각 언어가 있어야 한다.
- 제목은 차트가 무엇인지가 아니라 **무엇을 말하는지**("경기장별 개최 수" 대신 "고지대 경기장에서 득점이 적다" 식으로, 데이터가 뒷받침할 때만)

## 10. 접근성·기술

- 호버로만 드러나는 기능 금지. 포커스·탭으로도 접근 가능해야 한다.
- 버튼·내비 링크 텍스트가 두 줄로 줄바꿈되지 않게 (라벨 줄이기, `white-space: nowrap`, 좁은 화면에서 메뉴로 접기)
- 모바일 폭(약 375px)에서 가로 스크롤 없이 확인
- 히어로 이미지(LCP)에 `loading="lazy"` 금지. `fetchpriority="high"` 사용
- 동영상은 `autoplay muted loop playsinline` 네 개 모두
- `prefers-reduced-motion` 존중
- 다크 모드 지원 시 토큰으로 전환
- 키보드 사용자를 위해 포커스 표시가 항상 보이게(포커스 외곽선은 키보드의 커서다)
- 색만으로 의미를 전달하지 않는다(적록 색각 이상은 남성 약 12명 중 1명)

## 11. 제출 전 셀프 점검

만든 뒤 아래를 하나씩 확인하고, 걸린 항목은 고친 다음 제출한다. 무엇을 확인했고 무엇을 고쳤는지 짧게 보고한다.

- [ ] 장식용 그라데이션, 그라데이션 텍스트, 블롭/오브가 없다
- [ ] 색은 앵커 1 + 포인트 1 + 중립색이고, 모든 색에 의미가 있다
- [ ] 모든 색과 폰트가 토큰(`var(--...)`)으로 참조된다
- [ ] Inter 단독 사용이 아니고, 폰트 선택 이유를 말할 수 있다
- [ ] 이탤릭 제목, 모든 섹션 아이브로우, 2열 섹션 헤드가 없다
- [ ] 3열 똑같은 카드, 카드 안 카드, 한쪽 색 띠 카드가 없다
- [ ] 100vh 중앙 정렬 히어로, 전부 중앙 정렬이 아니다
- [ ] 내비·푸터가 이 사이트 장르에 맞다
- [ ] 의미 없는 배지, 깜빡이는 배지가 없다
- [ ] 이모지 아이콘이 없고 아이콘 라이브러리는 하나다
- [ ] 목적 없는 글래스모피즘, 가짜 OS 크롬이 없다
- [ ] 마케팅 과장어, 환영 문구, 제작 과정 언급, 지어낸 수치가 없다
- [ ] 정렬이 어긋난 요소가 없다
- [ ] `transition: all`, 모든 요소 hover scale, 모든 섹션 fade-up이 없다
- [ ] 모바일 폭에서 깨지지 않고, 버튼 라벨이 줄바꿈되지 않는다
- [ ] 버튼 레이블이 "확인/제출"이 아니라 결과를 말하고, 화면당 기본 행동이 하나다
- [ ] 버튼은 실행, 링크는 이동에만 쓰였고 서로의 모양을 흉내 내지 않는다
- [ ] 모든 필드에 바깥 레이블이 있고, 불필요한 필드가 없으며, 오류가 필드 옆에 뜬다
- [ ] 모달은 꼭 막아야 할 결정에만 썼고, 버튼이 결과를 말하며, Esc로 닫힌다
- [ ] 오류 메시지가 문제 위치와 복구 방법을 알려주고, 색만으로 표시되지 않는다
- [ ] 아이콘에 레이블(또는 툴팁)이 있다
- [ ] 체크박스/라디오/토글이 역할대로 쓰였다(토글 + 저장 버튼 조합 없음)
- [ ] 탭은 한 줄이고 병렬 콘텐츠에만 쓰였다
- [ ] 데스크톱에서 주요 내비가 햄버거 뒤에 숨어 있지 않다
- [ ] hover로만 접근 가능한 기능이 없고, 키보드 포커스가 보인다
- [ ] 글자 크기·반경·간격이 정해진 스케일 안에 있다
- [ ] (대시보드) 답할 핵심 질문이 있고, 가장 중요한 요소가 가장 크게 보인다
- [ ] (대시보드) 모든 차트에 축 제목·단위가 있고, 차트 하나에 지표 하나다
- [ ] (대시보드) 같은 숫자를 여러 번 반복하지 않고, 표가 화면 밖으로 잘리지 않는다
- [ ] (대시보드) 지어낸 데이터·비교가 없고, 결측과 로딩이 구분된다
- [ ] 한글이 의도한 폰트로 표시된다
