# 에니어그램 웹서비스 기능·운영 요구사항

> 기준 파일: `에니어그램_통합_기능확장_로컬프로토타입(1).html`  
> 목적: 현재 로컬 프로토타입을 실제로 운영 가능한 웹서비스로 발전시키기 위한 기능, 데이터, 검색, AI, 유지보수 요구사항 정리

---

## 0. 결론 요약

현재 서비스는 **정적 HTML + 브라우저 로컬 저장(localStorage)** 만으로도 꽤 많은 기능을 유지할 수 있다.

특히 아래 기능은 **별도 서버 없이 구현 가능**하다.

- 사이트 전체 텍스트 검색
- 유형/개념/FAQ/라이브러리 검색
- 북마크
- 최근 본 콘텐츠
- 유형 비교
- 성찰 기록
- 5Why
- 대시보드 집계
- 간단한 키워드 기반 유형 탐색 챗
- JSON 파일 기반 콘텐츠 관리
- 기록 내보내기/가져오기

반면 **실제 생성형 AI 챗봇**은 저장용 서버만 있다고 되는 것이 아니다.

- AI 답변 생성을 위해서는 LLM API 또는 별도 AI 모델 실행 환경이 필요하다.
- 브라우저 코드에 API Key를 직접 넣는 방식은 보안상 사용하면 안 된다.
- 가장 현실적인 구조는 **정적 사이트 + 작은 서버리스 함수 + AI API** 조합이다.
- 서버 자체 비용은 거의 없거나 무료 구간으로 시작할 수 있어도, **AI 호출 비용은 사용량에 따라 발생할 수 있다.**

따라서 1차 MVP에서는 다음을 권장한다.

> **전체 검색 + 로컬 가이드 챗 + 성찰 기록 + 대시보드 + 라이브러리/북마크**
>
> 실제 생성형 AI는 서비스 사용성이 확인된 뒤 2차로 붙인다.

# 1. 서비스 방향

## 1.1 서비스 핵심 목적

이 서비스는 사용자가 에니어그램 유형을 단순히 맞히는 것보다 다음 흐름을 경험하도록 한다.

1. 에니어그램 개념을 이해한다.
2. 나와 가까운 유형 후보를 탐색한다.
3. 헷갈리는 유형을 비교한다.
4. 실제 생활 장면을 기록한다.
5. 반복되는 반응과 동기를 관찰한다.
6. 기록이 쌓이면 나의 패턴을 확인한다.
7. 다음 행동을 작게 실험한다.

따라서 기능 설계도 **'유형 판정'보다 '자기관찰 → 비교 → 기록 → 패턴 발견'** 흐름을 우선한다.

# 3. 시스템 구조 권장안

## 3.1 단계별 구조

### A. 완전 로컬 / 서버 없음

```text
정적 HTML/CSS/JS
        ↓
콘텐츠 JSON
        ↓
브라우저 검색 인덱스
        ↓
localStorage / IndexedDB
```

가능한 기능:

- 전체 텍스트 검색
- 북마크
- 최근 본 콘텐츠
- 성찰 기록
- 유형 체크 결과 저장
- 대시보드 집계
- 키워드 기반 가이드 챗
- 라이브러리 필터
- JSON 내보내기/가져오기

장점:

- 서버 비용 없음
- 배포 단순
- 개인정보를 서버에 저장하지 않아도 됨
- 프로토타입 운영에 적합

한계:

- 다른 기기와 기록 동기화 불가
- 브라우저 데이터를 삭제하면 기록도 사라질 수 있음
- 회원 기능 불가
- 진짜 생성형 AI는 어려움
- 커뮤니티 운영 불가

---

### B. 작은 저장 서버만 추가

```text
Frontend
   ↓
간단한 API / BaaS
   ↓
DB
```

예:

- Supabase
- Firebase
- Cloudflare 계열 저장소
- 기타 간단한 BaaS

가능해지는 기능:

- 회원 로그인
- 여러 기기 기록 동기화
- 성찰 기록 백업
- 사용자별 북마크 저장
- 관리자 콘텐츠 등록
- 커뮤니티 데이터 저장

하지만 이 구조만으로는 **AI가 생기는 것은 아니다.**

AI 응답이 필요하다면 별도로 LLM API 또는 AI 실행 환경이 필요하다.

---

### C. 실제 AI 챗봇까지 추가

```text
Frontend
   ↓
Serverless Function
   ├─ 서비스 콘텐츠 검색
   ├─ 사용자 질문 정리
   └─ API Key 보호
        ↓
LLM API
```

권장 구조:

- 프론트엔드에 AI API Key를 넣지 않는다.
- 작은 서버리스 함수가 AI API를 대신 호출한다.
- 사이트 콘텐츠 중 관련 내용만 AI에 전달한다.
- AI는 서비스 내부 자료에 근거해 답변하도록 제한한다.
- AI 결과는 유형 확정이 아니라 비교 질문/자기관찰을 돕는 방향으로 설계한다.

아래 콘텐츠를 통합 검색한다.

- 기본적인 두려움

- FAQ

## 4.3 검색 방식

### MVP 권장: 브라우저 내 텍스트 검색

별도 서버 없이 구현한다.

구조:

```text
content/*.json
       ↓
search-index.json
       ↓
Fuse.js / MiniSearch / FlexSearch 등
       ↓
검색 결과
```

사이트 규모가 현재 수준이라면 서버 검색은 필요하지 않다.

---

## 4.4 검색 UX

검색창 위치:

- PC: 상단 헤더 우측
- 모바일: 메뉴 상단 또는 검색 버튼
- 단축키: `/` 또는 `Ctrl/Cmd + K` 선택 적용

검색창 클릭 시:

1. 최근 검색어
2. 자주 찾는 주제
3. 주요 유형
4. 최근 본 콘텐츠

를 보여줄 수 있다.

검색 결과 항목:

```text
[카테고리]
제목

검색어가 포함된 설명 일부...
> 해당 위치로 이동
```

예:

```text
[유형 비교]
3번과 6번은 무엇이 다를까요?

3번은 성취·가치와 관련된 동기를,
6번은 안전·신뢰와 관련된 동기를...
```

---

## 4.5 검색어 보정

간단한 동의어 사전을 둔다.

예:

```json
{
  "호나비언": ["호니비언", "Hornevian"],
  "사고형": ["사고 중심", "머리 중심"],
  "감정형": ["감정 중심", "이미지 중심"],
  "본능형": ["본능 중심", "장 중심"],
  "3번": ["성취자", "achiever"]
}
```

오타/표기 차이가 있어도 결과를 보여주는 것을 목표로 한다.

---

## 4.6 검색 결과 필터

필수는 아니지만 P1에서 추가한다.

- 전체
- 개념
- 유형
- 비교
- 성찰
- 라이브러리

---

## 4.7 검색 수용 기준

- 검색어 입력 즉시 결과가 갱신된다.
- Enter를 누르지 않아도 결과 확인 가능하다.
- 검색 결과에서 실제 콘텐츠 위치로 이동한다.
- 모바일에서도 동일하게 동작한다.
- 결과가 없을 때 추천 검색어를 제공한다.
- 한글/영문 표기 차이를 일부 흡수한다.
- 키보드만으로도 결과 선택이 가능하다.

# 5. AI 유형 탐색 요구사항

## 5.1 먼저 정의할 것

현재 로컬 기능은 실제 생성형 AI가 아니라 아래 방식에 가깝다.

> 미리 정의된 유형 데이터 + 키워드 탐지 + 질문 분기

이 방식도 충분히 가치가 있으므로, **MVP에서는 유지해도 된다.**

다만 실제 AI를 연결하지 않는다면 사용자에게 기능을 과장하지 않는다.

추천 명칭:

- 유형 탐색 챗
- 유형 비교 도우미
- 가이드 챗
- 로컬 탐색 모드

'AI 유형 탐색' 명칭을 유지할 경우 `LOCAL GUIDE MODE` 등을 명확하게 표시한다.

---

# 6. AI 기능 개발 단계

## Level 0. 현재 방식 유지

비용:

- 서버 비용 없음
- AI API 비용 없음

동작:

- 사용자가 유형 A/B 선택
- 실제 상황 입력
- 키워드 추출
- 후보 유형의 동기/두려움 비교
- 다음 질문 제시

적합한 목적:

- 3번 vs 6번
- 4번 vs 9번
- 1번 vs 6번처럼 헷갈리는 유형 비교

---

## Level 1. 로컬 검색 + 대화형 답변 조립

생성형 AI 없이도 조금 더 자연스럽게 만들 수 있다.

예:

```text
사용자 질문
↓
질문의 핵심 키워드 추출
↓
사이트 내부 관련 문서 검색
↓
관련 문장 3~5개 추출
↓
미리 만든 답변 템플릿에 삽입
```

예:

> "제가 3번인지 6번인지 모르겠어요."

답변:

> 두 유형 모두 일을 열심히 할 수 있지만 이유가 다를 수 있어요.  
> 3번은 '잘해내고 가치 있는 사람으로 보이는 것'이 중요할 수 있고  
> 6번은 '문제가 생기지 않도록 충분히 확인하는 것'이 중요할 수 있어요.
>
> 최근에 일을 많이 했던 장면 하나를 떠올려볼까요?
>
> **성과가 안 나오는 것**과 **잘못될 가능성** 중 어떤 쪽이 더 불편했나요?

이 정도는 서버 없이 가능하다.

---

## Level 2. 실제 생성형 AI

사용자가 자유롭게 문장을 입력하고 AI가 상황에 맞춰 질문을 이어가는 방식이다.

필수 구성:

- Serverless Function
- LLM API
- 프롬프트 관리
- 사이트 콘텐츠 검색
- 사용자 입력 필터링
- 호출량 제한
- 오류 처리

---

## 6.1 실제 AI에서 반드시 지켜야 할 응답 원칙

AI는 다음을 하지 않는다.

- "당신은 3번입니다"처럼 유형 확정
- 정신건강 진단
- 치료 또는 상담 대체
- 사용자의 한 문장만 보고 유형 단정
- 타인의 유형 판정

AI는 다음을 한다.

- 두 후보 유형의 차이를 설명
- 실제 장면을 요청
- 행동보다 동기를 질문
- 반대 가능성도 함께 제시
- 관련 사이트 콘텐츠로 연결
- 성찰 기록으로 이어주기

---

## 6.2 AI 답변 기본 구조

```text
1. 사용자가 말한 상황 요약
2. 현재 보이는 후보 동기 2개
3. 두 유형의 차이
4. 구분을 위한 질문 1~2개
5. 관련 콘텐츠 링크
6. 성찰 기록으로 저장하기
```

---

## 6.3 AI 비용 최소화 원칙

- 모든 질문에 AI를 호출하지 않는다.
- 먼저 로컬 검색으로 답할 수 있는 질문은 로컬에서 처리한다.
- 단순 개념 질문은 미리 작성한 콘텐츠를 사용한다.
- 자유로운 상황 분석이 필요한 경우만 AI 호출한다.
- 대화 전체를 매번 보내지 말고 핵심 대화 요약만 전달한다.
- 답변 길이를 제한한다.
- 일일/월간 사용량 제한을 둔다.

# 7. 추천 검색 + AI 결합 구조

가장 권장하는 방식이다.

```text
사용자 질문
    ↓
1. 사이트 내부 검색
    ↓
관련 콘텐츠 존재?
 ├─ YES → 검색 결과 + 요약 제공
 └─ NO
      ↓
2. AI 질문으로 전환
      ↓
관련 유형/개념 데이터 전달
      ↓
AI 답변
```

장점:

- AI 호출 횟수 감소
- 답변의 일관성 증가
- 잘못된 답변 감소
- 서비스 내부 자료 활용 증가
- 비용 절감

# 13. 추가 추천 기능

## 13.1 최근 본 콘텐츠

## 13.2 용어 사전

대상:

- 에고

- 하모닉
- 날개

- 성장/스트레스 방향

## 13.3 관련 콘텐츠

각 페이지 아래 자동 추천한다.

예:

```text
지금 3번 유형을 보고 있어요.

함께 보면 좋은 내용
- 3번 vs 6번
- 감정 중심
- 주장형
- 3번의 성장 방향
```

---

## 13.4 '처음이라면 여기부터'

첫 방문자가 기능을 이해하기 어려울 수 있으므로 간단한 시작 플로우를 만든다.

```text
처음 방문
↓
에니어그램 3분 이해
↓
간편 유형 체크
↓
유형 후보 2개 보기
↓
두 유형 비교
↓
실제 장면 기록
```

---

## 13.5 나의 유형 가설

사용자가 유형을 확정하지 않고 후보를 저장한다.

예:

```text
현재 탐색 중

1순위 3번
2순위 6번

헷갈리는 이유
- 일을 많이 함
- 평가를 신경 씀
- 동시에 실패 가능성도 계속 확인함
```

유형을 '정답'으로 저장하는 대신 **가설 상태**로 관리한다.

---

## 13.6 성장 실험

성찰 기록에서 적은 '다음에 다르게 해볼 행동'을 별도로 모은다.

예:

```text
이번 주 성장 실험

[ ] 회의에서 내 의견 한 번 말하기
[ ] 확인 메시지를 한 번 덜 보내기
[ ] 도움을 주기 전에 내가 원하는 것도 확인하기
```

대시보드와 연결한다.

# 25. AI 도입 의사결정 기준

아래 질문 중 3개 이상 YES일 때 실제 AI를 붙이는 것을 권장한다.

- 사용자가 자유 질문을 많이 하는가?
- 미리 만든 비교 시나리오만으로 대응하기 어려운가?
- 같은 질문도 상황에 따라 다른 후속 질문이 필요한가?
- 사용자가 자신의 긴 경험을 설명하고 분석받고 싶어 하는가?
- 내부 콘텐츠가 충분히 정리되어 있는가?
- AI API 비용을 감당할 운영 계획이 있는가?
- AI 오답을 관리할 정책이 있는가?

그 전에는 로컬 가이드 챗이 더 싸고 안정적이다.

# 26. 구현 시 중요한 금지사항

## 보안

- 프론트엔드에 AI API Key 삽입 금지
- 소스 코드에 관리자 비밀번호 삽입 금지
- 사용자 입력 HTML 직접 삽입 금지
- 커뮤니티 도입 시 HTML sanitize 필수

## 데이터

- 저장 구조를 버전 없이 변경하지 않음
- 기존 localStorage key를 무작정 삭제하지 않음
- 사용자 기록을 업데이트 과정에서 초기화하지 않음

## UX

- 에니어그램 유형을 확정적 진단처럼 표현하지 않음
- AI가 유형을 단정하게 하지 않음
- 성찰 기록 입력을 강제하지 않음
- 사용자가 적은 기록을 동의 없이 외부 AI에 보내지 않음

# 29. 최종 추천

현재 단계에서는 **서버나 AI부터 붙이지 않는 것이 좋다.**

먼저 아래 4개를 완성하는 편이 서비스 퀄리티에 더 크게 영향을 준다.

1. **전체 검색**
2. **콘텐츠/데이터 구조 분리**
3. **성찰 기록 안정화**
4. **로컬 유형 탐색 챗 고도화**

이 구조만으로도 사용자가

> "궁금한 걸 찾고 → 유형을 비교하고 → 내 실제 경험을 기록하고 → 반복 패턴을 확인하는"

하나의 완성된 경험을 만들 수 있다.

이후 실제 사용자가 자유 질문을 많이 하기 시작하면,

> **정적 사이트 + Serverless Function + LLM API**

구조로 AI를 추가하는 것이 가장 효율적이다.
